# قلمینو (Ghalamino) — بک‌اند فروشگاه لوازم‌التحریر

بک‌اند این پروژه با Django REST Framework نوشته شده و شامل موارد زیر است:

- احراز هویت با **شماره تلفن** بر پایه‌ی **کد یک‌بارمصرف (OTP)** — بدون پسورد
- JWT (`simplejwt`) برای نگه‌داشتن نشست کاربر + خروج با blacklist کردن refresh token
- **محصولات** با دسته‌بندی و برند (`apps/store`)
- **سبد خرید** (`apps/cart`)
- **سفارش‌ها** (`apps/orders`)
- **پرداخت** با اتصال به درگاه‌های **سیزپی** و **سپهر (بانک صادرات)** (`apps/payment`)
- مستندات **Swagger / OpenAPI** با `drf-spectacular`
- پوشه‌ی اصلی تنظیمات پروژه: `config`

## ساختار پروژه

```
ghalamino/
├── config/                 # تنظیمات اصلی پروژه
├── apps/
│   ├── accounts/            # احراز هویت OTP + JWT
│   ├── store/                 # محصول / دسته‌بندی / برند
│   ├── cart/                    # سبد خرید
│   ├── orders/                    # سفارش‌ها
│   └── payment/                     # پرداخت چند-درگاهی (sizpay, sepehr, ...)
├── manage.py
├── requirements.txt
└── .env.example
```

## راه‌اندازی

```bash
python -m venv venv
source venv/bin/activate

pip install -r requirements.txt
cp .env.example .env          # مقادیر از جمله SIZPAY_* / SEPEHR_* را ویرایش کنید

python manage.py makemigrations
python manage.py migrate
python manage.py createsuperuser   # برای ورود به پنل ادمین جنگو (این حساب پسورد دارد)

```

## احراز هویت — `/api/v1/accounts/` (بدون پسورد، بر پایه‌ی OTP)

کاربران عادی **هیچ پسوردی ندارند**. ورود و ثبت‌نام یکی هستند: اگر شماره تلفن قبلاً وجود نداشته باشد، در لحظه‌ی تایید کد،
حساب به‌صورت خودکار ساخته می‌شود.

| متد       | مسیر             | توضیح                                                                                                          |
|-----------|------------------|----------------------------------------------------------------------------------------------------------------|
| POST      | `otp/request/`   | با `phone_number`، یک کد OTP تولید و پیامک می‌کند                                                              |
| POST      | `otp/verify/`    | با `phone_number` و `code`؛ در صورت صحت، کاربر را (در صورت نبودن) می‌سازد و `access`/`refresh` JWT برمی‌گرداند |
| POST      | `token/refresh/` | گرفتن access جدید با استفاده از refresh                                                                        |
| POST      | `logout/`        | نیازمند احراز هویت؛ refresh token را blacklist می‌کند                                                          |
| GET/PATCH | `profile/`       | نیازمند احراز هویت؛ مشاهده/ویرایش پروفایل (نام، ایمیل)                                                         |

### نمونه‌ی فلوی ورود

```bash
# ۱) درخواست کد
curl -X POST http://127.0.0.1:8000/api/v1/accounts/otp/request/ \
  -H "Content-Type: application/json" \
  -d '{"phone_number": "09121234567"}'

# ۲) تایید کد (کد در حالت توسعه در لاگ سرور چاپ می‌شود، چون SMS_BACKEND=console است)
curl -X POST http://127.0.0.1:8000/api/v1/accounts/otp/verify/ \
  -H "Content-Type: application/json" \
  -d '{"phone_number": "09121234567", "code": "12345"}'
# → { "user": {...}, "access": "...", "refresh": "..." }
```

### نکات امنیتی OTP

- کد به‌صورت **هش‌شده** (با همان الگوریتم هش پسورد جنگو) در دیتابیس ذخیره می‌شود، نه متن ساده.
- هر کد فقط `OTP_EXPIRY_SECONDS` ثانیه (پیش‌فرض ۱۲۰ ثانیه) معتبر است.
- بین دو درخواست کد برای یک شماره، حداقل `OTP_RESEND_COOLDOWN_SECONDS` ثانیه (پیش‌فرض ۶۰) باید فاصله باشد.
- بعد از `OTP_MAX_VERIFY_ATTEMPTS` (پیش‌فرض ۵) تلاش ناموفق برای وارد کردن کد، آن کد باطل می‌شود.
- روی هر دو اندپوینت `otp/request/` و `otp/verify/` یک throttle عمومی (`5/min` بر اساس IP، در
  `REST_FRAMEWORK.DEFAULT_THROTTLE_RATES['otp']`) هم فعال است.
- کاربرانی که با OTP ساخته می‌شوند `unusable password` دارند (پسورد اصلاً وجود ندارد) — فقط حساب‌های ادمین/staff که با
  `createsuperuser` ساخته می‌شوند پسورد واقعی دارند و برای ورود به `/admin/` استفاده می‌شود.

### سرویس پیامک (SMS Provider)

اتصال به سرویس پیامک پشت یک انتزاع ساده در `apps/accounts/sms.py` قرار دارد:

- **`console`** (پیش‌فرض، برای توسعه): کد واقعاً پیامک نمی‌شود، فقط با `logger.warning` در کنسول/لاگ سرور چاپ می‌شود —
  یعنی همین الان بدون هیچ سرویس پیامکی می‌توانید کل فلو رو تست کنید.
- **`kavenegar`**: نمونه پیاده‌سازی برای سرویس Lookup (پترن) کاوه‌نگار. کافیست در `.env`:
  ```
  SMS_BACKEND=kavenegar
  KAVENEGAR_API_KEY=<کلید API از پنل کاوه‌نگار>
  KAVENEGAR_OTP_TEMPLATE=<نام پترن تاییدشده در پنل>
  ```
  برای provider های دیگر (ملی‌پیامک و ...) کافیست کلاسی با همان امضای متد `send_otp(phone_number, code)` در `sms.py`
  اضافه و در تابع `get_sms_provider()` رجیستر کنید.

| متد  | مسیر                     | توضیح                                                                          |
|------|--------------------------|--------------------------------------------------------------------------------|
| GET  | ``                       | لیست سفارش‌های کاربر                                                           |
| POST | `create/`                | ساخت سفارش از روی سبد خرید (آدرس گیرنده در بدنه درخواست)                       |
| POST | `shipping-estimate/`     | پیش‌نمایش هزینه ارسال سبد خرید فعلی (با `{"province": "..."}`)، بدون ثبت سفارش |

روند ثبت سفارش: موجودی هر محصول بررسی و رزرو (کسر) می‌شود، قیمت لحظه‌ی خرید در `OrderItem` ذخیره می‌شود، هزینه‌ی ارسال
طبق بخش زیر محاسبه و در `Order.shipping_cost` ذخیره می‌شود، و در پایان سبد خرید خالی می‌شود.

### هزینه ارسال (پست پیشتاز)

هنگام ثبت سفارش (`orders/create/`)، هزینه‌ی ارسال به‌صورت خودکار محاسبه و در `shipping_cost` سفارش ذخیره می‌شود؛
منطق آن در `apps/orders/shipping.py` است و بر این اساس کار می‌کند:

1. وزن کل مرسوله از روی وزنِ هر آیتم ضرب‌در تعدادش جمع زده می‌شود: اگر آیتم یک تنوع (رنگ/سایز) خاص از محصول
   باشد و برای همان تنوع وزنی (`ProductVariant.weight_grams`) ثبت شده باشد، همان استفاده می‌شود؛ در غیر این
   صورت وزنِ خودِ محصول (`Product.weight_grams`، به گرم) به کار می‌رود. برای مواردی که وزنشان اصلاً ثبت نشده،
   مقدار `DEFAULT_PRODUCT_WEIGHT_GRAMS` (پیش‌فرض ۲۰۰ گرم) جایگزین می‌شود.
2. بر اساس وزن کل و استان مقصد (تهران در برابر سایر استان‌ها)، هزینه از روی جدول تعرفه‌ی پست پیشتاز خوانده
   می‌شود؛ برای وزن‌های بالاتر از بیشترین سقف جدول، به‌ازای هر کیلوگرم اضافه، یک هزینه‌ی ثابت به هزینه افزوده
   می‌شود.
3. اگر `FREE_SHIPPING_THRESHOLD` (تومان) تنظیم شده و جمع قیمت کالاها به آن برسد، ارسال رایگان می‌شود (پیش‌فرض
   غیرفعال است).

جدول تعرفه و هزینه‌ی هر کیلوگرم اضافه دیگر در کد/تنظیمات هاردکد نیستند و از **پنل ادمین** قابل ویرایش‌اند:

- **جدول تعرفه پست پیشتاز** (مدل `ShippingTariffRow` در اپ `orders`): هر ردیف شامل سقف وزن (گرم)، هزینه‌ی
  تهران و هزینه‌ی سایر استان‌هاست؛ از پنل ادمین می‌توان ردیف اضافه/ویرایش/حذف کرد.
- **تنظیمات هزینه ارسال** (مدل `ShippingSettings`، تک‌ردیفی): شامل «هزینه اضافه به ازای هر کیلوگرم مازاد»
  است.

بنابراین برای به‌روزرسانی تعرفه‌ی رسمی شرکت ملی پست ایران، نیازی به تغییر کد یا دیپلوی مجدد نیست و کافی است
از پنل ادمین ویرایش شود.

برای پیش‌نمایش هزینه‌ی ارسال پیش از ثبت نهایی سفارش (مثلاً در صفحه‌ی سبد خرید)، اندپوینت زیر موجود است:

| متد  | مسیر                 | دسترسی        | توضیح                                                                                      |
|------|----------------------|---------------|--------------------------------------------------------------------------------------------|
| POST | `shipping-estimate/` | نیازمند لاگین | با `{"province": "..."}` هزینه‌ی ارسال سبد خرید فعلی کاربر را برمی‌گرداند (بدون ثبت سفارش) |

## اندپوینت‌های پرداخت — `/api/v1/payment/`

دو درگاه پیاده‌سازی شده‌اند: **سیزپی (SizPay)** و **سپهر (پرداخت الکترونیک بانک صادرات)**.
معماری درگاه‌ها (`apps/payment/gateways/`) از یک کلاس پایه‌ی انتزاعی (`BasePaymentGateway`) و یک
factory (`PaymentGatewayFactory`) استفاده می‌کند؛ برای افزودن درگاه جدید کافی‌ست کلاسی مشابه
`sizpay.py`/`sepehr.py` بسازید و در `factory.py` رجیستر کنید.

مقدار `gateway` هنگام ساخت پرداخت یکی از `sizpay` / `sepehr` است.

سیزپی و سپهر به‌جای یک لینک GET ساده، نیازمند هدایت کاربر با یک فرم POST خودکار (چند فیلد مخفی)
به صفحه‌ی بانک هستند؛ برای همین `payment_url` این دو درگاه به یک صفحه‌ی واسط داخلی اشاره می‌کند
(`GatewayRedirectView` در `redirect/<gateway>/<payment_id>/`) که این فرم را می‌سازد و خودکار
submit می‌کند - فرانت‌اند کافی‌ست کاربر را به همین `payment_url` هدایت کند.

| متد      | مسیر                               | دسترسی        | توضیح                                                                                                                                                              |
|----------|------------------------------------|---------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| POST     | `create/`                          | نیازمند لاگین | با `{"order": <id سفارش>, "gateway": "sizpay"\|"sepehr"}` یک تراکنش می‌سازد و `payment_url` برمی‌گرداند                                                            |
| POST     | `verify/`                          | نیازمند لاگین | با `{"authority": "..."}` پرداخت را نزد درگاه verify می‌کند (برای صدا زدن دستی از فرانت‌اند؛ برای سپهر معمولاً لازم نیست چون callback خودش verify را انجام می‌دهد) |
| GET      | `redirect/<gateway>/<payment_id>/` | عمومی         | صفحه‌ی واسط auto-submit فقط برای `sizpay`/`sepehr`                                                                                                                 |
| GET/POST | `callback/sizpay/`                 | عمومی         | آدرس بازگشتی (ReturnURL) سیزپی                                                                                                                                     |
| GET/POST | `callback/sepehr/`                 | عمومی         | آدرس بازگشتی (callbackURL) سپهر                                                                                                                                    |

### روند پرداخت

1. کاربر سفارش می‌سازد (`orders/create/`) → وضعیت سفارش `pending_payment`
2. فرانت‌اند به `payment/create/` با `{"order": <id>, "gateway": "..."}` درخواست می‌زند و کاربر را به
   `payment_url` برگردانده‌شده هدایت می‌کند (برای سیزپی/سپهر این آدرس یک صفحه‌ی واسط داخلی است که
   خودکار کاربر را با POST به بانک منتقل می‌کند)
3. کاربر در درگاه پرداخت را انجام می‌دهد (یا لغو می‌کند) و بانک او را به `callback/...` مربوطه بازمی‌گرداند
4. بک‌اند پرداخت را نزد درگاه verify/تایید می‌کند (سیزپی: Confirm، سپهر: Advice)؛
   در صورت موفقیت، وضعیت سفارش به `paid` و `paid_at` تنظیم می‌شود، در غیر این صورت وضعیت سفارش به
   `failed` تغییر می‌کند
5. اگر `FRONTEND_ORDER_RESULT_URL` تنظیم شده باشد، کاربر با کوئری‌پارامترهای `order_number`, `status`, `ref_id` به
   آن صفحه ریدایرکت می‌شود؛ وگرنه پاسخ JSON مستقیم از بک‌اند برمی‌گردد

### تنظیمات لازم

```
BACKEND_BASE_URL=https://yourdomain.com   # بدون / انتهایی - برای ساخت لینک صفحه‌ی واسط سیزپی/سپهر

# سیزپی - این ۵ مقدار پس از عقد قرارداد از پنل سیزپی دریافت می‌شود
SIZPAY_MERCHANT_ID=<کد پذیرنده>
SIZPAY_TERMINAL_ID=<کد ترمینال - ۸ رقمی>
SIZPAY_KEY=<کلید رمزنگاری AES - کلید ۱ - Base64>
SIZPAY_IV=<IV رمزنگاری AES - کلید ۲ - Base64>
SIZPAY_SIGN_KEY=<کلید امضای الکترونیکی HMAC-SHA256>
SIZPAY_CALLBACK_URL=https://yourdomain.com/api/v1/payment/callback/sizpay/   # باید دقیقاً همین آدرس مطلق باشد

# سپهر (بانک صادرات) - پس از عقد قرارداد و ثبت IP سرور از واحد پذیرندگان دریافت می‌شود
SEPEHR_TERMINAL_ID=<شماره ترمینال - ۸ رقمی>
SEPEHR_CALLBACK_URL=https://yourdomain.com/api/v1/payment/callback/sepehr/

FRONTEND_ORDER_RESULT_URL=https://yourdomain.com/order-result          # اختیاری
```

> **نکته واحد پول:** قیمت‌ها در کل پروژه به **تومان** ذخیره می‌شود، اما **سیزپی و سپهر هر دو
> صراحتاً مبلغ را به ریال** می‌خواهند؛ به همین دلیل `apps/payment/gateways/sizpay.py` و `sepehr.py` قبل از ارسال، مبلغ
> را در
> `TOMAN_TO_RIAL_MULTIPLIER` (پیش‌فرض `10`) ضرب می‌کنند. اگر واحد ذخیره‌سازی سفارش‌ها در پروژه‌ی
> شما تغییر کرد، حتماً این مقدار را هم بازبینی کنید.

> **نکته مهم درباره‌ی سیزپی:** فیلد `InvoiceNo` طبق مستند رسمی باید کاملاً عددی باشد، در حالی که
> شماره سفارش پروژه فرمت `GLM-xxxxxxxxxx` دارد؛ به همین دلیل یک شناسه‌ی عددی مجزا از UUID پرداخت
> ساخته می‌شود (`OrderID` همچنان همان شماره‌ی سفارش است، چون محدودیت عددی ندارد).

> **نکته مهم درباره‌ی سپهر:** برخلاف سیزپی، سپهر توکن را در callback برنمی‌گرداند؛ تطبیق
> تراکنش با `invoiceID` (که همان شماره سفارش است) انجام می‌شود. همچنین «رسید دیجیتال» لازم برای
> مرحله‌ی Advice (تایید نهایی) فقط در همان callback ارسال می‌شود، پس روی `Payment.extra_data`
> ذخیره می‌شود.

### افزودن یک درگاه جدید (مثلاً زرین‌پال، آیدی‌پی، نکست‌پی و ...)

معماری در `apps/payment/gateways/` است:

1. یک فایل جدید مثل `idpay.py` در همان پوشه بساز
2. کلاسی از `BasePaymentGateway` (در `base.py`) ارث‌بری کن و دو متد را پیاده‌سازی کن:
    - `create_payment(payment)` → `{'authority': ..., 'payment_url': ...}`
    - `verify_payment(payment)` → `{'success': bool, 'ref_id': ..., 'card_pan': ...}`
3. مقدار جدید را به `PaymentGateway.choices` در `models.py` و به شرط‌های `PaymentGatewayFactory.get_gateway` در
   `factory.py` اضافه کن، و یک migration بساز
4. کلید(های) API لازم را به `settings.py` و `.env` اضافه کن

همین چهار قدم کافی است — `views.py`، `urls.py` و `serializers.py` بدون هیچ تغییری با درگاه جدید کار می‌کنند، چون
`Payment.gateway`, `Payment.authority` و `Payment.ref_id` عمومی و مستقل از هر درگاه خاصی طراحی شده‌اند.

## مستندات Swagger

- Swagger UI: `http://127.0.0.1:8000/api/docs/`
- Redoc: `http://127.0.0.1:8000/api/redoc/`
- Schema خام: `http://127.0.0.1:8000/api/schema/`

برای تست اندپوینت‌های محافظت‌شده در Swagger UI، دکمه Authorize را بزنید و `Bearer <access_token>` را وارد کنید.

## پیشنهادهایی برای تکمیل پروژه

1. **دفترچه آدرس (Address Book)** — در حال حاضر آدرس گیرنده مستقیماً روی هر سفارش ذخیره می‌شود؛ یک مدل `Address` مجزا با
   امکان چند آدرس و آدرس پیش‌فرض تجربه بهتری می‌دهد.
2. **کد تخفیف / کوپن** — مدل `Coupon` (درصدی/مبلغ ثابت، تاریخ انقضا، سقف استفاده) قابل‌اعمال در ساخت سفارش.
3. **لغو خودکار سفارش‌های پرداخت‌نشده** — چون موجودی هنگام ثبت سفارش رزرو می‌شود، یک تسک زمان‌بندی‌شده (Celery Beat)
   برای لغو سفارش‌های `pending_payment` قدیمی‌تر از مثلاً ۳۰ دقیقه و بازگرداندن موجودی لازم است.
4. **captcha یا محدودیت سخت‌گیرانه‌تر روی otp/request** — throttle فعلی بر اساس IP است؛ برای جلوگیری از حملات
   توزیع‌شده (چند IP روی یک شماره) یک لایه‌ی محدودسازی سخت‌گیرانه‌تر (مثلاً reCAPTCHA یا محدودیت هم‌زمان per-phone در
   سطح کش/Redis) پیشنهاد می‌شود.
5. **نظرات و امتیاز محصولات (Reviews & Ratings)**.
6. **لیست علاقه‌مندی‌ها (Wishlist)**.
7. **مدیریت موجودی دقیق‌تر** — تاریخچه تغییرات انبار (Inventory Log).
8. **کش با Redis** — برای اندپوینت‌های پرترافیک مثل لیست محصولات.
9. **تست‌های خودکار** — `pytest-django` برای مدل‌ها، سریالایزرها و به‌خصوص فلوی حساس OTP و پرداخت (mock کردن SMS
   provider و درگاه‌های پرداخت).
10. **لاگ و مانیتورینگ خطا** — اتصال Sentry، به‌خصوص برای فلوی پرداخت و ارسال پیامک.
11. **Docker / docker-compose** — برای استانداردسازی محیط توسعه و دیپلوی (Postgres + Redis + Gunicorn + Nginx).
12. **پنل ادمین فارسی‌تر** — تقویم شمسی با `django-jalali`.

اگه بخوای، پیشنهاد می‌کنم مورد ۳ و ۴ (لغو خودکار سفارش و سخت‌گیری بیشتر روی OTP) رو زودتر از بقیه اضافه کنیم، چون
مستقیماً به امنیت و صحت موجودی مرتبط هستن.
